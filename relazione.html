1A
Introduzione
Obiettivo · Contesto · Problema

Obiettivo del progetto

Il progetto consiste nella realizzazione di un sito web informativo dedicato al Campionato Mondiale di Motociclismo 2026 (Motomondiale). L'obiettivo principale è offrire un'unica piattaforma che raccolga classifiche, risultati, schede piloti, pronostici e statistiche per MotoGP, Moto2 e Moto3, in un'interfaccia moderna, responsiva e dotata di un sistema di account sicuro per salvare i piloti preferiti.

Contesto

Il sito è ospitato su GitHub Pages come applicazione statica, ma è integrato con un servizio Backend-as-a-Service (Supabase) per la gestione degli account utente. Mentre i contenuti informativi (classifiche, risultati) sono incorporati nel frontend per garantire massima velocità di caricamento, l'autenticazione e i dati personali (preferiti) risiedono su un database PostgreSQL cloud, garantendo sicurezza e accessibilità da qualsiasi dispositivo.

Problema da risolvere

I siti ufficiali sono spesso lenti e appesantiti. Il progetto vuole offrire un'alternativa veloce che metta al centro l'informazione tecnica. Inoltre, rispetto a un classico sito statico, si voleva superare il limite del salvataggio locale dei dati (cookie/localStorage) introducendo un sistema di autenticazione reale, che permetta all'utente di ritrovare i propri preferiti su qualsiasi browser o telefono.

Analisi dei Requisiti
Funzionali · Non funzionali · HW/SW

Analisi applicativa

Il dominio applicativo è l'informazione sportiva. Gli utenti sono appassionati che vogliono consultare rapidamente classifiche e schede piloti. L'interazione avviene tramite browser. È richiesto un sistema di registrazione e login per abilitare la funzionalità "Piloti Preferiti", che deve persistire a livello cloud (associato all'account) e non più al singolo browser.

Requisiti hardware e software

Client
Qualsiasi device
PC, Mac, smartphone, tablet. Browser moderno (Chrome, Firefox, Safari, Edge).
Frontend Hosting
GitHub Pages
Hosting statico gratuito per i file HTML/CSS/JS. CDN globale e HTTPS automatico.
Backend & DB
Supabase (BaaS)
Servizio cloud per autenticazione utenti, database PostgreSQL e Row Level Security (RLS).

Requisiti funzionali

  • Il sistema deve permettere la visualizzazione delle classifiche e risultati per le tre categorie, con dati embedded nel frontend.
  • Il sistema deve permettere la registrazione e autenticazione tramite email, supportando anche il login tramite "Username" custom oltre all'email.
  • Il sistema deve permettere agli utenti autenticati di aggiungere/rimuovere piloti dai preferiti. I preferiti devono essere salvati nel database cloud.
  • Le password devono essere crittografate (hashing bcrypt) e gestite dal backend. Nessuna password in chiaro nel frontend.
  • Il sistema deve garantire che un utente possa leggere e modificare esclusivamente i propri preferiti, senza poter accedere a quelli di altri.

Requisiti non funzionali

Prestazioni: caricamento iniziale sotto 2 secondi su 4G. I dati informativi sono embedded per evitare ritardi di rete; il DB viene interrogato solo per le funzionalità utente.
Responsività: layout adattivo per schermi da 320px a 2560px. Breakpoint principale a 1100px (hamburger) e 768px (colonne mobili).
Sicurezza: utilizzo di Row Level Security (RLS) su PostgreSQL. Le chiavi segrete (Service Role) non sono mai esposte nel frontend, che usa solo la chiave pubblica (Publishable Key) abbinata alle policy RLS.

Progettazione
Architettura · Struttura · Dati

Architettura generale

Il sito segue un'architettura ibrida: il frontend è statico e ospita i dati informativi, mentre delega al Backend-as-a-Service (Supabase) la logica di account e persistenza dei preferiti. Il frontend comunica con il backend tramite le API REST di Supabase usando una chiave pubblica sicura.

HTML5→ struttura semantica
CSS3→ variabili custom, grid, media query
JavaScript ES2022→ rendering dinamico, manipolazione DOM
Supabase BaaS→ Auth (JWT), PostgreSQL, RLS Policy
Service Worker→ cache offline (PWA)
localStorage→ cache UI (tema, audio), token sessione Supabase

Struttura delle pagine

  • index.html — Home: notizie, countdown prossimo GP, top-5 classifiche, calendario.
  • piloti.html / pilota.html — Lista e scheda dettagliata dei 97 piloti. In queste pagine operano le stelline per aggiungere ai preferiti.
  • guida.html — Manuale utente: spiega come navigare e come funziona il sistema di Account e Preferiti.
  • relazione.html — Documentazione tecnica del progetto.

Struttura dei dati JavaScript (Frontend)

I dati informativi (classifiche, risultati) sono organizzati in oggetti JavaScript costanti:

Struttura della Navigazione
Header · Mobile Menu · Routing

Sistema di navigazione multi-breakpoint

La navigazione è gestita interamente in CSS e JavaScript vanilla. L'header è sticky (rimane fisso durante lo scroll) con z-index 200. Contiene tre componenti: logo, nav desktop e div header-right con toggle tema, pulsante "Accedi/Avatar Utente" (iniettato da auth.js) e hamburger.

Gestione del tema scuro/chiaro

Il tema è implementato tramite l'attributo HTML data-theme="dark|light" sull'elemento radice <html>. Tutte le pagine usano lo stesso set di CSS Custom Properties ridefinite nel selettore [data-theme="light"]. La preferenza viene salvata nel localStorage.

Motivazioni delle scelte

La scelta di Supabase come backend è dettata dalla necessità di avere un sistema di account reale e sicuro senza dover scrivere un server Node.js o PHP da zero. Supabase gestisce l'hashing sicuro delle password (bcrypt) e offre query PostgreSQL dirette dal frontend, rendendo l'ambiente estremamente sicuro se abbinato alle policy RLS. Questo permette di mantenere l'hosting su GitHub Pages (gratuito e statico) pur avendo un database cloud potente.

5A
Implementazione
Funzionalità chiave · Codice · Pattern

Sicurezza e Autenticazione Cloud (Supabase)

Tutta la logica di autenticazione è centralizzata in un file auth.js, incluso in tutte le pagine che necessitano di login. Questo file inizializza il client Supabase usando una chiave pubblica (Publishable Key), progettata per essere esposta nel frontend. La sicurezza non si basa sul nascondere la chiave, ma sulle Row Level Security (RLS) del database.

Login tramite Email o Username

Supabase Auth usa nativamente l'Email per il login. Per permettere all'utente di loggarsi anche con lo Username, è stata creata una funzione RPC (Remote Procedure Call) in PostgreSQL sicura (SECURITY DEFINER). Questa funzione riceve l'identificativo (email o username) e la password, verifica internamente l'hashing bcrypt, e restituisce l'email associata solo se le credenziali sono corrette, evitando di esporre gli account a scansione pubblica.

// auth.js — Flusso di Login const isEmail = identifier.includes('@'); if (!isEmail) { // Se non è un'email, chiama la RPC sicura per ottenere l'email const { data } = await supabase.rpc('get_email_by_credentials', { p_identifier: identifier, p_password: password }); loginEmail = data; // Ora abbiamo l'email reale } // Login standard con Supabase Auth const { data, error } = await supabase.auth.signInWithPassword({ email: loginEmail, password });

Protezione dei Preferiti (RLS)

La tabella PostgreSQL favorites memorizza i piloti preferiti. Su questa tabella sono state imposte le seguenti policy RLS:

  • SELECT: Un utente può leggere solo le righe dove user_id = auth.uid().
  • INSERT: Un utente può inserire una riga solo se il campo user_id corrisponde al proprio ID.
  • DELETE: Un utente può eliminare solo le proprie righe.

Grazie a queste policy, anche se un utente malintenzionato scrivesse codice malevolo nella console del browser, il database PostgreSQL rifiuterà qualsiasi modifica ai preferiti di un altro utente.

Pattern architetturale: render dinamico dal JS

Le tabelle classifiche non sono scritti staticamente nell'HTML ma generati da funzioni JavaScript che leggono i dati dagli oggetti DATA e costruiscono il markup con template literals.

Funzionalità UX implementate

  • Scorciatoie da tastiera — tasti M, 2, 3, C, R, P, H e /.
  • Bottone "Torna indietro" dinamico — implementato con sessionStorage.
  • Animazioni fade-in scroll — IntersectionObserver con stagger di 60ms.
  • Prediction — pagina pronostici (prediction.html) con layout ad accordion per i round, Smart Entry List che esclude infortunati, generatore casuale e calcolo dinamico del "Pilota Favorito" salvato nel localStorage.
  • Statistiche — pagina dati (stats.html) con Indice di Dominanza (gauge SVG), andamento punti top-5, record.
  • Albo d'oro — esteso con categorie storiche (350cc, 50cc, 80cc, Sidecar), filtri per decadi.

Nessuna dipendenza JavaScript esterna

La scelta di non usare framework (React, Vue) elimina il problema del "bundle size". Il frontend scarica solo il file HTML della pagina richiesta e la libreria di Supabase (necessaria per l'auth). I dati informativi sono embedded, quindi le chiamate di rete si limitano allo stretto necessario per le funzionalità account.

Accessibilità e Usabilità
ARIA · Keyboard · UX

Accessibilità da tastiera

Tutta la navigazione del sito è raggiungibile da tastiera. I bottoni interattivi hanno attributi aria-label per i lettori di schermo. Il toggle tema ha aria-label="Cambia tema".

Principi UX applicati

Feedback visivo immediato: ogni elemento interattivo cambia aspetto all'hover con transizioni CSS di 150ms.

Stato Utente chiaro: nell'header, l'utente non loggato vede un pulsante "👤 Accedi", mentre l'utente loggato vede il proprio avatar con le iniziali del username. Cliccando l'avatar, si apre un menu a tendina che mostra i preferiti e il pulsante di logout.

Sviluppi Futuri
Miglioramenti · Scalabilità

Dati in tempo reale

L'evoluzione naturale prevede l'uso delle API ufficiali MotoGP per popolare il database Supabase automaticamente dopo ogni sessione, eliminando l'aggiornamento manuale dei dati embedded.

Notifiche push

Tramite le Push API del browser (già supportate dai Service Worker PWA) e le notifiche di Supabase, si potrebbe notificare l'utente al termine di ogni sessione con il vincitore.

Applicazione nativa

Il sito è già installabile come PWA. Per una vera app nativa su App Store/Google Play si potrebbe usare Capacitor (Ionic) che avvolge il codice HTML/JS esistente in un container nativo.

7A
Conclusioni
Risultati · Valutazione · Criticità

Il progetto ha raggiunto tutti gli obiettivi: un sito informativo completo, navigabile da qualsiasi dispositivo, e dotato di un sistema di account cloud sicuro e funzionante su più dispositivi grazie a Supabase.

Risultati ottenuti

  • 43 pagine HTML funzionanti con navigazione coerente, tema scuro/chiaro.
  • 97 piloti con scheda completa, palmares e grafico punti per round.
  • Sistema di Login/Registrazione con email/username sicuro, basato su Supabase e PostgreSQL.
  • Tabella preferiti protetta da Row Level Security (RLS).
  • Installabile come app su Android, iOS e desktop grazie alla tecnologia PWA.

Criticità incontrate e soluzioni

Vecchio sistema basato su localStorage: Il progetto iniziale salvava utenti e preferiti nel browser tramite localStorage e usava un debole offuscamento (btoa) per le password. Questo limitava l'uso a un singolo browser e non era sicuro. Risolto: migrazione completa a Supabase Auth, che usa hashing bcrypt server-side e JWT token per le sessioni.

Login tramite Username: Supabase non supporta nativamente il login con solo username. Risolto: creazione di una funzione RPC PostgreSQL sicura che mappa lo username all'email verificando preventivamente la password.

Valutazione complessiva

Il progetto dimostra come sia possibile realizzare un'applicazione web completa, combinando le prestazioni di un sito statico (HTML, CSS, Vanilla JS) con la potenza di un backend reale (Supabase), senza l'onere di gestire un'infrastruttura server propria.
